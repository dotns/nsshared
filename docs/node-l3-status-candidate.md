# Node L3 route admission and applied status

Ordinary Node-L3 rules govern direct identity-derived N6/N4 destinations. A Subnet mapped-prefix destination is resolved to its exact resource and selected route, never converted into a Node-L3 destination rule naming the provider. Neither a Subnet permission nor provider membership opens direct N6/N4 access. NodeL3 and NodeL3Authority bytes are unchanged. Independent service admission retains its existing source ownership and remains separate from ordinary host permission.

On the provider, admit a mapped-prefix packet only through the current Exit owner's exact join of resource, authenticated client and provider, grant incarnation, payer and expiry, the embedded validated route's real/mapped selection minus exclusions and its SubnetProxyCoverage, and validated local enablement/binding. Preserve existing resource-authority/payer joins and retirement. A client route view alone cannot authorize service. On the client, the current authenticated `subnet-routes` view authorizes selecting only its named resource's selected mapped destinations and covered TCP/UDP/echo traffic for the route's provider: compare client with self and provider with the independently installed peer identity/key, within the existing accepted source and Network. This is permission to select that route, not provider-side grant authority. Neither side creates or requires a Node-L3 rule for this mapped-prefix path. Direct N6/N4 traffic still needs its independent authority; route withdrawal, exclusion or missing coverage cannot fall back to a provider-wide Node rule. Preserve bypass data and its existing routing semantics, source/destination ownership, and established reverse-flow ownership. Real IPv6 forwarding and live default Exit remain outside the existing scope.

Provenance is unchanged: NSD produces provider Exit grants and the separate client route view from committed permission, mapping, offers and selection; authenticated source publications carry them under the respective recipient's current nodes binding. The Subnet validator derives the selected cover and protocol coverage from those route bytes. Local configuration and validated Linux state produce provider enablement/binding, and peer installation supplies authenticated identity/key ownership. Each side compares its own current inputs as above; the client neither receives nor fabricates provider payer/incarnation facts.

The pure shared confidential operation `node.l3.status` uses BootstrapEnvelope for family 11, kind `node-l3`, snapshot events. It is available to the authenticated recipient Node, including a gateway. Do not reuse the legacy Node-L3 ACK, M6 SnapshotAck or heartbeat policy_version. There is no separate accepted-only phase: only actual enforcement application can produce Applied.

The canonical request is `[1, request_id, key, source_binding_bytes, event_version, event_digest, status]`. `request_id` is a recipient-produced nonzero 16-byte byte string identifying its pending report. `key` is `[issuer, recipient, served_realm, scope, 11, "node-l3"]`, using full 32-byte identity byte strings, canonical RealmId ULID text and the existing publication scope text. `source_binding_bytes` is a byte string containing the existing `SourceBinding::canonical()` bytes, copied from the independently accepted SignedSourceBinding; it carries every source field, not just its generation, without duplicating the binding signature. Its NSD/recipient/realm/scope must match the key. `event_version` is the positive enclosing event version; a nonempty Data NodeL3Authority must have matching NodeL3 issuer, recipient and revision. `event_digest` is exactly 32 bytes: SHA-256(ASCII `ns.account.node-l3.v1` || one zero byte || `PublicationEvent::canonical()` of the signed inner event). It includes the inner signature and all publication metadata and payload, but excludes the outer SourcePublication and delivery context. Retransmission of the same retained inner event therefore retains its digest; its source is separately compared in full. Do not hash a re-created policy or only NodeL3Authority bytes. Reuse the existing domain_digest helper without changing its contract.

`status` is exactly `[0]` for Applied, `[1, reason]` for Rejected, or `[2]` for FetchFailedDenied. The rejection reason is nonempty UTF-8 text of at most 256 bytes without control characters and grants no authority. Applied means the recipient's current enforcement has installed that exact Data event's replacement, including completed removal for a complete-empty withdrawal. FetchFailedDenied is only for a verified authenticated FetchFailed event after its exact collection has been denied. Rejected reports a verified event that could not be installed; it is never applied evidence. Unauthenticated input and outer fetch failure produce no report purporting to identify an authenticated issuance. Existing invalid-input, version/tombstone and expiry rules remain unchanged. Use strict canonical CBOR and existing control/source/publication bounds; unknown statuses and extra fields fail.

The request uses the normal confidential authenticated Request envelope with operation `node.l3.status`, signer equal to key.recipient and envelope recipient equal to key.issuer. NSD uses existing authentication/source authorization and compares the full key, all binding fields, version and digest with its retained current issuance for that recipient; a report's own values cannot establish that expected context. NSD retains the exact signed inner event and its source when issuing it and computes the same digest. Only a matching Applied Data report establishes applied evidence for that issuance. Rejected and FetchFailedDenied never become affirmative permission evidence; an Applied empty withdrawal proves removal, not access. A superseded source or issuance cannot satisfy the current predicate. Existing policy_required and effective-authority checks remain independent; successful report transport does not authorize a resource.

A successful Response envelope from that NSD to the Node echoes the normal pending envelope nonce and carries `[1, bstr(exact_canonical_request)]`. The Node compares the full echoed request bytes, including request_id and status, with its pending report under existing envelope trust/direction/operation checks. This is receipt of the exact status, not an assertion of remote data-plane observation. A mismatch or refusal is not a success receipt. Request IDs correlate reports; they do not replace event identity or source fencing.

The runtime carries the accepted key, source, event bytes/version/digest from the control writer to the enforcement application result. The Node compiler supplies the actual install/deny result for that collection; the status sender compares that result with the still-current accepted context before reporting it. A global maximum revision, aggregate rule count, successful decode, queued installation or a diagnostic counter cannot substitute for this association. This requires only the narrow local application association/readback and report adapter, not a new shared enforcement runtime or a change to other collections' ownership.

## Independent acceptance

`node_l3_route_admission_vectors` distinguishes mapped selection from direct host
permission. `node_l3_applied_status` fixes signed event digest bytes, canonical
reports, exact receipts, replaced-source and same-version/different-event fencing,
rejection, authenticated FetchFailed denial and complete-empty removal.

| --- | --- | --- | --- |
