## Exact JWT string preservation

The exact claim-name/value join incorrectly used the whitespace-free label
validator. Gateway claim lookup and equality preserve raw strings, including
spaces and empty strings. The implementation constrains
these two data fields only by valid UTF-8 and the existing 256-byte bound.
The descriptive `jwt_claim_strings_preserve_exact_values` regression is retained.
The same predicate audit covers subject names, credential/authority/material
references, header names, destination matchers, URL realm/route labels and scope
tokens; their existing syntax restrictions remain appropriate and unchanged.

### Text validation coverage

| Values | Validation after the correction |
| --- | --- |
| JWT claim names and values | Exact UTF-8 data, zero through 256 bytes; no normalization |
| Policy subject labels and credential anchors | Existing nonempty, whitespace/control-free label check |
| JWT authority and header keyset references | Existing reference check |
| Signed subject header names | Existing label check plus lowercase HTTP-token syntax |
| Credential scopes and policy destination sets | Existing label check, ordering and collection bounds |
| Signed URL realm and route | Existing label check plus scope-separator refusal |

The similarly named M6 text extractor only checks the CBOR text variant, and
CBOR writers copy original UTF-8 bytes. Neither applies the subject-label
predicate to claim data; no additional implementation site needs a change.
