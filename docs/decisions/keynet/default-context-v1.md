# Keynet default-context profile v1

Selected on 2026-09-16 for the coordinated client and relay change. This profile
supersedes user-facing network creation, selection and ownership. It does not
revise the Keynet v1 wire layouts or the sealed v0.7 conformance release.

## Shared identifier

`keynet_proto::DEFAULT_NETWORK_ID` is the single implementation constant. Its
32 bytes are SHA-256 of ASCII `keynet-default-context-v1` without a newline:

```text
953ead48b53d57f072706b6a5d400037c8baf02f1f516cef60a83b17b6902c02
```

This public value is a wire scope, not a public key derived from a distributed
private key. No shared signing secret or network-owner authority exists. All
clients use these exact bytes in the existing `network_id` fields, address,
relay-slot and pair-PSK derivations. Changing the bytes changes addresses, slots
and pairing scope, so this value must not be made deployment-configurable.

## Authentication and authorization

Bindings, pairing tokens, relay registrations and revocations retain device
signatures and their existing generation, expiration and replay checks.
New tokens retain the twelve-field v1 layout and emit `net_name = ""`.
Clients reject a token with a different `network_id` before mutating state;
`net_name` is neither authority nor a value to display. The generic v1 codecs
remain able to decode and verify legacy scopes for conformance and diagnostics.

The relay accepts arbitrary 32-byte scopes: it verifies device signatures,
derives the slot from scope and identity, and forwards only between equal
scopes. Shared relay reachability is not authorization. The relay does not store
the client pairing graph; each client must enforce explicit, independent peer
authorization. A pairing between A and B and one between B and C grants no
A-to-C access. Existing admission, rejection, removal and rotation rules remain.

The legacy two-signature `NameRecord` API requires a scope signing key and is
not enabled in this profile. It remains unchanged for v1 conformance. Clients
must neither publish nor install network-authorized names for this context.

## Client integration contract

- Public commands, help, configuration, errors, status and JSON omit the network
  concept, including any selectable or displayed default network.
- Identity labels and local nicknames remain. DNS names use
  `<nickname>.keynet.internal`, `<identity-label>.id.keynet.internal`, and their
  `<nickname>.v4.keynet.internal` / `<identity-label>.id.v4.keynet.internal`
  counterparts. Legacy generic naming helpers are not the client DNS contract.
- Public JSON advances to v2 and configuration schema to 2 without network
  fields; the old public output contract is not retained. Wire v1 version
  numbers do not change. Internal v1 IPC may remain, but new process boundaries
  reject legacy scope-management operations.
- Ordinary startup does not rewrite legacy state. Explicit upgrade backs it up,
  preserves device identity and requires fresh pairing; addresses may change.
  Backup and restore must be validated by the client implementation.

Client state migration, DNS, JSON and pairwise access enforcement belong to the
client repository. This shared profile alone does not prove those capabilities.

## Validation and fixture boundary

The existing `tests/fixtures/keynet-v1` release, its manifest and digest pin stay
byte-for-byte unchanged. New derivations live in the separate
`crates/keynet-proto/tests/fixtures/default-context-v1` directory, generated by
`tests/generate_default_context_vectors.py` using Python's standard library,
without calling Rust or creating signing keys. Run the generator with `--check`
to detect drift. Rust integration tests consume these independently generated
address, slot and identity-label vectors and check device-signed pairing with
an empty legacy display name and recipient enforcement.

Relay registration, forwarding and durable identity isolation are validated in
the relay repository. Real Linux TUN, direct/relay traffic, non-transitive
authorization, restart, rotation and migration remain final client integration
obligations; relay forwarding tests alone cannot close them.
